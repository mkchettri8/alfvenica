# Pass 2 calculation replay contract

## Schema decision (recorded before implementation)

The browser exporter keeps `org.alfvenica.reproducible-calculation-record/1.0.0` and `org.alfvenica.deterministic-calculation-state/1.0.0` unchanged. Their canonical internal inputs, stable formula ID, output values and units, active warning IDs, constants, and serialized state suffice for a numerical replay under the *current* registry. Display inputs, display outputs, export time, and text labels are presentation or export context. The v1.0.0 record has no independently verified source commit, no formula-definition version, no explicit replay tolerance, and no assessed model-compatibility status. A reader must report these absent facts as `not_available_from_v1_0_0`; it must not infer historical software identity from the present checkout or treat no active warning as compatibility.

Node-created replay records use `org.alfvenica.reproducible-calculation-record/2.0.0`. They retain the v1 calculation and deterministic-state fields and add a `replay` block: formula-definition content identity, declared numerical comparison rule, structured warning IDs and `not_assessed`/`warning_active` applicability status, optional user-declared semantic assumptions, Node runtime version, and a verified content identity for the exact local source files used by the new route. `replay.producer` separately identifies the **Alfvenica research runner** as `DEVELOPMENT_UNRELEASED`, names record schema v2.0.0 and the underlying application v1.1.0, and declares that this runner was `NOT_PART_OF_BASE_RELEASE`. Its metadata is checked before replay. The underlying v1.1.0 application/core provenance remains factual; the new runner makes no v1.1.0 release-membership claim. No Release 2 version, DOI, tag, or release date is assigned.

The formula identity hashes the registry definition, including equation, input and output metadata, assumptions and decision IDs; it is **not** a proof that the implementation matches the equation. The source identity hashes file bytes; it is **not** a Git commit, mission-file checksum, build-output checksum, or scientific validation. The released `sourceCommit: null` claim stays unchanged.

The reader accepts only the two named record versions. For v1.0.0 it takes internal input values and units from `calculation.inputs`, compares them with the deterministic state, and reports any inconsistency; it does not invent a formula version or verified software identity. Deterministic-state inputs must also match the current registry's key, semantic ID, quantity and canonical unit; formula LaTeX, review status and decision IDs must agree with the record/current formula. Regenerating a serialized string after changing those fields cannot make the state consistent. The reader compares every declared output and warning ID. For v2.0.0 it additionally verifies declared formula and source-content identities. Unknown schemas, malformed inputs, wrong input units, missing formula IDs, contradictory producer metadata, and non-finite supplied inputs fail structurally. No interval data, quality flag, source-file identity, or Wind processing provenance is invented by this calculation-only format.

The replay numerical rule is `|current − saved| ≤ 1e−12 × max(|current|, |saved|)` for finite numeric outputs, with zero absolute tolerance; categorical outputs and warning-ID sets use exact equality. This is an explicit computational comparison allowance for binary64 implementations, not measurement uncertainty or evidence of scientific correctness. A saved non-finite output is compared by its declared special-value token. Changed values, warning IDs, state strings, formula identity and software identity have separate report fields.

No SHA-256 calculation-state digest is introduced in this pass. The v1 canonical serialization remains available and is checked during replay; a later digest would need browser/CommonJS and migration-level canonicalization and tamper demonstrations before claiming state identity.

## Local API and commands

`require('./research-runner.js')` exposes `run(state)`, `runMany(states)`, `createRecord(state)`, `replay(record)`, and `sourceIdentity()`. A state is `{formula_id, canonical_inputs, input_units?}`; keys and units must match the existing formula and unit registries. `runMany` returns one result per supplied state, including structured errors for bad states. A successful result has `outputs` (key, kind, value, special value, internal unit), first `value` and `unit` for convenience, formula identity, structured warnings and warning IDs, `evidence_class: not_assessed`, `record_evidence_class: P_PROVENANCE`, and applicability `warning_active` or `not_assessed`. Neither absence of warnings nor arithmetic success is a physical compatibility finding. The result also contains the existing exporter record; it does not use a second physics implementation.

`createRecord` takes the same state, with optional `declared_assumptions` strings and `source_data` object. Those are user declarations, saved for interpretation and provenance but **not verified** by the calculation runner. The returned v2 JSON record can be saved using `JSON.stringify(record, null, 2)`. The CLI reads either v1 or v2 JSON:

```bash
node examples/wind_pilot/create_pass2_record.js > examples/wind_pilot/pass2_proton_beta_record.json
npm run replay -- examples/wind_pilot/pass2_proton_beta_record.json
npm run build:research
```

The first command rebuilds a **single** Pass 1 representative proton trace-beta record from accepted canonical numbers and source-file attribution. It does not ingest CDF rows or re-screen quality flags. `npm run replay` prints JSON and exits 0 for `MATCH` or `MATCH_ENVIRONMENT_DIFFERS`, 2 for `MISMATCH` or `PROVENANCE_MISMATCH`, and 1 for an invalid or unsupported record. `npm run build:research` prints the current source-set manifest calculated from file bytes. The v2 record embeds that manifest as its development build identity; replay recomputes and compares it. A changed tracked source file therefore makes the saved record's software identity differ even if the numerical output happens to match. Regenerate an example record after editing one of the listed execution files.

The content identity includes the named physics, registry, guardrail, export, runner, replay, metadata, and build entry-point files. It is produced by the new Node build/record path from actual bytes and reports `sourceCommit: null` because it makes **no verified Git checkout claim**. It is a source-set identity, not a generated-standalone hash. The historical v1.1.0 standalone and its released source-commit-unavailable statement remain frozen. If a future Release 2 artifact is published, its release process must carry this content manifest into that artifact and verify the published bytes; this Pass 2 development record does not claim such a release exists. The separate Wind CDF SHA-256 in the example record is a caller-declared **data-file** identifier and is not checked against a local CDF by this runner.

Replay separately reports `calculation_match` (outputs, warning IDs, deterministic state and declared warning/applicability metadata), `implementation_provenance_match` (formula/source identity and available application/constants/core/equation metadata), and `environment_match` (Node runtime version, or `not_available_from_v1_0_0`). `match` means the first two are true. For v2 records, `MATCH` also has matching runtime provenance; `MATCH_ENVIRONMENT_DIFFERS` has reproducible calculation and implementation with a different Node version. `PROVENANCE_MISMATCH` means calculation matches but implementation provenance differs. `MISMATCH` means a numerical output, warning or deterministic calculation-state comparison differs. Runtime mismatch alone is visible and does not cause a failing exit code. For v1.0.0 records, original software/formula version and explicit applicability metadata remain `not_available_from_v1_0_0`; a numerical match cannot prove the unavailable original checkout. Unsupported schema versions and invalid internal units/inputs fail before a scientific value is returned. The command supplies no event interpretation, archive-quality verification, uncertainty, interval analysis, or independent validation.
